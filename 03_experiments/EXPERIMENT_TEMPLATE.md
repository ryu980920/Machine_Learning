# 공통 실험일지 양식 (EXPERIMENT_TEMPLATE)

이 문서는 팀원 4명이 실험을 같은 기준으로 기록하기 위한 **AI 상호 확인 규칙 + 복사용 양식**입니다.
핵심은 **문제 발견 → 원인 가설 → 방법 선택 → 실제 수행 절차 → 검증 근거 → 결과 → 최종 판단**입니다.

**개정 목적:** 작업 결과만 요약하는 일지가 아니라, 다른 팀원이 **어떤 데이터를 골라 어떤 코드·설정으로 처리했는지 재현할 수 있는 일지**를 만든다. 특히 자료에 정보가 빠졌을 때 AI가 실험자에게 **질문 또는 증빙 자료를 요청하는 과정**을 반드시 거친다.
초기 모델 학습처럼 아직 문제가 없는 경우에는 '문제' 대신 '검증할 질문'을 작성합니다.

## 교수님 지침에 따른 전원 필수 실험 요소 (향후 적용)

**팀원 4명 모두** 독립적으로 개발용 데이터의 (1) 오류/혼동 클래스·대표 이미지, (2) Original vs Hand-made 데이터 특징의 정량 비교, (3) 자동 전처리 Pipeline 또는 Training Augmentation 가설 및 전후 비교, (4) Accuracy·Macro F1·학습/전처리/예측 시간·실패 사례·재현 코드 근거를 자기 주차의 실험일지에 기록한다. **데이터 분석을 전담자 한 사람에게만 몰아주지 않는다.** 모델 담당이 누구든 동일 원칙을 따른다.

**데이터 사용 권한:** 기존 2,560장 및 개발용 Validation에서는 오류·분포·Confusion Matrix 분석이 가능하다(학습/검증 누출 방지). 교수님 **1차는 최초 고정 모델의 Test**로 쓰며, 성능이 만족스러우면 그대로 보고한다. 부족할 때는 교수님 직접 허용에 따라 **1차를 Validation으로 전환**하고 오분류·특성 분석·전처리 및 모델 최적화에 사용할 수 있다. 이때 1차 결과를 더 이상 독립 Test라 하지 않는다. **2차는 최종 Test로 단 한 번만** 평가하고 이후 수정하지 않는다. Original Test 16,000장도 하이퍼파라미터 결정에 사용하지 않는다.

**전처리 경계:** 원본 파일을 사람 손으로 미리 수정·재저장하는 Cleaning과 **모델 일부인 자동 입력 Pipeline**, **Training에만 적용하는 Augmentation**을 따로 기록한다. Test 데이터에 맞춰 Pipeline 파라미터를 정하지 않는다.

## 1. 팀원과 AI를 위한 작성 규칙

이 파일을 ChatGPT·Claude·Gemini 등 다른 AI에 제공할 때도 아래 기준을 적용합니다.

1. **실제 자료만 근거로 작성**합니다. 실험자의 메모, 실행한 Notebook, 저장된 실행 출력, CSV 및 그래프를 확인합니다. 코드에 설정이 있다고 해서 해당 실행이 성공했다고 추측하지 않습니다.
2. **없는 사실을 만들지 않습니다.** 미확인 수치, 실행하지 않은 실험, 실제로 선택하지 않은 방법, Seed, 결과·원인은 임의로 채우지 않습니다.
3. 자료로 확인할 수 없는 정보는 우선 **담당자에게 질문하거나 증빙 자료를 요청**합니다. 답변이 아직 없으면 `확인 필요`, 적용되지 않으면 `해당 없음`, 아직 측정하지 않았으면 `미측정`·`미실시`로 표시합니다. **빈칸을 임의의 기본값으로 채우거나 질문 없이 최종 완료 처리하지 않습니다.**
4. **실험자의 의도는 실험자에게서 확인**합니다. 왜 그 방법을 선택했는지 코드만으로 판단하지 않습니다. 메모가 없으면 `확인 필요`로 표시합니다.
5. 문제로 **관찰된 현상(사실)**과 **원인에 대한 설명(가설)**을 구분합니다. 단순한 성능 향상을 원인 입증으로 표현하지 않습니다.
6. 실제 사용한 **입력 파일·버전·개수, 데이터 분할 시점·Seed, 함수·파라미터·처리 순서, 출력 파일, 검증 결과**를 남깁니다. 모델 실험에서는 Training/Validation/평가 데이터, 모델·주요 Hyperparameter와 학습 Seed를 기록합니다. Seed의 **적용 대상**을 구분합니다.
7. 비교 실험에서는 **무엇을 바꾸고 무엇을 고정했는지** 적습니다. 데이터나 평가 조건이 달라졌다면 성능 변화의 원인을 단정하지 않습니다.
8. 결과에는 **실측 수치와 근거 파일**을 연결하고, 문제를 해결했는지/어떤 추가 검증이 필요한지를 판단합니다. 실패·보류한 실험도 삭제하지 않습니다.
9. 교수님 지침에 따라 기존 Hand-made는 **Combined 학습 및 개발용 Validation**으로 사용 가능하나 학습에 들어간 이미지/작성자를 같은 Fold의 독립 Validation으로 사용하지 않습니다. 교수님 **1차는 최초 Test 후 필요 시 Validation으로 전환 가능**, **2차는 최종 Test 1회 전용**입니다. 정답 없는 추정 레이블을 실제 정답이라 표시하거나 그것만으로 정확도를 계산하지 않습니다.
10. 아래 **실험일지 본문**의 제목·항목 순서를 유지합니다. 해당하지 않는 항목은 `해당 없음`으로 남길 수 있습니다. 불필요한 배경 설명과 반복을 줄이고 간결한 대학생 연구일지 문체를 사용합니다.
11. AI는 **일지를 정리하는 보조자**입니다. 실험자가 작성된 조건과 결과를 마지막으로 확인하고, 잘못된 해석을 수정한 뒤 등록합니다.
12. 작성 중 **재현이나 결과 판단에 필요한 정보가 빠지면, AI가 담당자에게 먼저 구체적으로 질문**합니다. 질문에 대한 답 또는 자료를 받은 후 일지에 반영하며, 해결되지 않은 핵심 항목이 있으면 `초안/확인 대기`로 남겨 **최종 완료 처리하지 않습니다.**

### AI의 필수 작업 순서 — 부족한 정보는 질문 후 확정

아래 절차는 **모든 팀원의 AI(ChatGPT·Claude·Gemini 등)가 따르는 필수 규칙**이다. AI가 자료를 읽고 일지를 한 번에 작성했다고 해서 완성으로 간주하지 않는다.

1. **자료 확인:** 이번 주 팀장 작업 지시서, 제출된 Notebook·스크립트·실행 출력·결과 파일·이전 로그를 먼저 확인한다. 코드에 적힌 설정과 **실제로 실행되어 결과가 나온 설정**을 구분한다.
2. **사실 추출 및 누락 점검:** 무엇을 했는지(수행 단계), 어떻게 했는지(함수·설정·대상·순서), 왜 했는지(실험자 의도), 어떤 결과를 확인했는지(수치·검증)가 자료에서 확인되는지 살핀다.
3. **필수 정보가 부족하면 질문:** **최종 실험일지를 확정하기 전에** 팀원에게 필요한 질문을 직접 제시한다. 함수 이름이 불명확하면 사용한 코드 셀이나 파일을, 실행 여부가 불명확하면 실제 실행 출력이나 산출물을 요청한다. 단순히 `확인 필요`라고 써 놓고 종료하지 않는다.
4. **질문 방식:** 한 번에 우선순위가 높은 질문 **3–7개 내외**로 묶고, 각 질문에 **(a) 이미 확인된 정보, (b) 무엇이 부족한지, (c) 정확한 질문 또는 필요한 자료, (d) 왜 필요한지**를 간략히 적는다. 답이 자료에 이미 있으면 다시 묻지 않는다. 질문은 실제 과제에 필요한 내용에만 한정한다.
5. **회신 반영:** 팀원이 답하거나 자료를 추가하면 답변·코드·결과를 대조하여 3절 수행 절차와 4절 결과를 보완한다. 여전히 핵심 정보가 비어 있으면 필요한 질문만 추가한다. 답을 추측하거나 질문에 대한 답을 대신 만들어 내지 않는다.
6. **최종화 판단:** 근거가 충분하면 `완료`, 필수 수행 방법·실행 결과·검증 근거 등이 없으면 `초안 / 확인 대기`로 표기한다. 팀원이 답할 수 없다고 명시한 경우에도 미확인 사실을 그대로 표시하고 제한점을 기록한다.
7. **실험 유형에 맞춰 질문:** 이론적 **모델 선정**만 수행한 사람에게 Accuracy·Epoch·학습 Seed를 요구하지 않는다. 반대로 **데이터 증강**을 수행한 사람에게는 원본 선정 기준, 이동·회전·획 두께 변환의 정확한 함수·범위·적용 대상·생성 수량·품질 검사를 우선 확인한다.

**질문이 필요한 경우 AI의 첫 응답 형식**

| 우선순위 | 이미 확인된 내용 | 팀원에게 묻거나 요청할 사항 | 필요한 이유 |
|---|---|---|---|
| 필수 | [현재 자료에서 확인한 내용] | [답변 가능한 구체적인 질문 또는 Notebook 셀·출력 파일 요청] | [재현/검증/선택 이유 확인] |
| 권장 | [현재 확인된 내용] | [추가 확인 질문] | [후속 비교에 필요한 이유] |

- 질문 아래에 **현재까지 확인된 사실 요약**을 짧게 작성할 수 있다.
- 필수 질문에 대한 회신이 없으면 **최종본 대신 '초안 / 확인 대기'**라고 밝힌다.
- 질문 없이 일지 작성이 가능한 경우에는 **'필수 누락 정보 없음'**을 먼저 명시하고 최종본을 작성한다.

**예시 — 데이터 증강 기록에 '±1–2픽셀 이동으로 6,659장 생성'이라고만 적혀 있는 경우**

- 이동 증강에 사용한 **실제 코드 셀/함수**를 알려 주세요. 수평·수직 이동량은 각각 어떤 범위에서 어떤 방식으로 뽑았나요?
- **어떤 원본 이미지를 몇 번씩 선택**해 증강했나요? 클래스별 선택 기준과 Seed·복원추출 여부를 확인할 수 있나요?
- Train/Validation을 **언제 분리**했으며, 증강에 사용한 원본과 변형본이 서로 다른 분할에 들어가지 않았는지 검사했나요?
- 변환 이미지의 **글자 잘림·판독 가능 여부**를 검사했나요? 실행 출력이나 원본/증강 비교 이미지를 제공할 수 있나요?

이 질문은 **자료에서 이미 답을 찾은 경우에는 반복하지 않는다.** 회전·획 두께 조절 등을 실제로 시행하지 않았다면 시행 여부부터 묻고, 수행하지 않은 방법의 파라미터를 지어내지 않는다.

### AI에 함께 제공할 자료

- 이 템플릿 파일
- 실제 Notebook(`.ipynb`) 또는 코드, 저장된 실행 결과·CSV·그래프
- 실험자 메모: **무슨 문제/질문이 있었나? → 왜 그 방법을 선택했나? → 결과를 어떻게 판단했나?**
- 이어진 실험이라면 이전 실험일지 링크

AI 요청 예시:
> 이 파일의 규칙을 따라 이번 주 실험일지를 작성해 줘. **먼저** 작업 지시서, Notebook, 실제 실행 결과·산출물을 확인해서 사실과 누락 정보를 분리해 줘. **필수 정보가 없으면 일지를 최종 확정하지 말고 나에게 구체적으로 질문하거나 필요한 코드·결과 파일을 요청해 줘.** 내가 답하면 그 내용을 증거와 대조한 후 수행 순서·함수·파라미터·검증 근거까지 기록해 최종 Markdown을 만들어 줘. 확인되지 않은 수행 여부·수치·선택 이유는 추측하지 마.

### 일지 운영 원칙

- **하나의 실험일지에는 하나의 핵심 질문**을 기록합니다. 한 질문에 대한 여러 파라미터 조합은 결과 CSV와 표로 묶어도 됩니다.
- 실험 시작 시 1–3번을 작성하고, 실제 수행 후 4–5번을 완성합니다.
- 작성한 일지는 예를 들어 `logs/EXP김001_초기모델.md`처럼 **실험 ID + 작성자 약칭 + 주차 내 001부터 시작하는 3자리 번호**로 관리합니다. 파일은 실험을 시작할 때 만듭니다.
- 일지는 핵심 사실과 판단 위주로 간단히 작성하고, 상세 설정·대량의 결과는 관련 Notebook/CSV에 연결합니다.
- 아래 구분선 다음의 **실험일지 본문만 복사**해 개별 일지를 작성합니다.

**실제로 수행한 과정 — 단계별 필수 표**

'다운로드 → 증강 → 저장'처럼 작업명만 적지 않는다. **어떤 입력에 무엇을 어떤 설정으로 적용했는지** 과정별로 분리한다. 아직 실행하지 않은 단계는 반드시 `계획`이라고 표시한다.

| 단계·상태 | 입력·대상·선정 기준 | 실제 수행 함수·방법·설정값 | 중간/최종 결과(개수·파일) | 실행·검증 근거 |
|---|---|---|---|---|

| 2 / 수행·계획 | [앞 단계 결과] | [실제 변환 순서·파라미터] | [생성 수량·파일] | [실행 로그·이미지] |
| 3 / 수행·계획 | [앞 단계 결과] | [저장 방법·검사 기준] | [최종 버전·개수] | [assert, CSV, 검증 출력] |

- **변경한 조건·특이사항:** [복수 변수 변경, 데이터 누출 가능성, 검증 미실시, 비교의 한계]
- **재현을 위한 실행 안내:** [입력 파일 → 실행 Notebook/스크립트 → 산출 파일 경로. 미확인이면 AI가 요청]

**작업 유형별 추가 확인 — 관련 유형만 사용**

| 유형 | 빠지면 AI가 질문해야 할 정보 |
|---|---|
| 데이터셋 구성 | 원본 출처·원본 Train/Test 사용 범위, 클래스 선택 기준, 클래스별 개수, 중복 정의 및 검사, 분할 시점·방법·Seed, 최종 레이블 매핑 |
| 데이터 증강 | **원본 선택 기준, 증강 적용 대상, 이동/회전/획 두께 조절의 실제 함수·파라미터, 보간·경계값, 변환 조합 및 순서, 클래스별 증강 수량, 글자 잘림·품질 검사, 원본/증강본의 Train–Validation 누출 여부** |
| 모델 선정·조사 | 검토한 후보 전체, 다중 클래스 방식, 학습 원리 차이, 후보 축소 기준, 선정·보류·제외 이유, 최종 선정 모델과 후속 계획 |
| 모델 학습·평가 | 모델 구현 클래스, 실제 Hyperparameter·학습/분할 Seed, 전처리·스케일링의 적용 대상, 학습·수렴 상태, 동일 Validation에서 Accuracy·Macro F1·Confusion Matrix·시간 등 **실측 여부** |
| 전처리 파이프라인 | 입력 원본, 변환 함수·적용 순서·파라미터, 학습과 추론의 적용 범위, Train/Validation 변환 일관성, 전후 비교 지표 |
| 오류·데이터 특성 분석 | 개발용 데이터의 **오류 클래스·작성자·실제 이미지 근거**, 중심/기울기/크기/밝기/획 굵기 등 분포·특징 계산법, 실제 측정과 원인 가설 구분 |
| 전처리·증강 비교 | Raw/Pipeline 및 증강 전/후 중 **독립적으로 변경한 조건**; 적용 순서·함수·Train-only 여부·품질·원본 보존, Validation 공정성, 정상/악화 사례 |
| 교수님 1차 / 2차 | **1차 최초 평가**에서는 모델·Pipeline 사전 고정. 부족하면 **1차를 Validation으로 전환 후** 오류 분석·최적화 가능(독립성 상실). **2차는 최종 Test 단 1회**, 이후 분석·튜닝 금지. Original Test는 별도 평가 전용 |

> **해당 없는 항목에는 질문하지 않는다.** 학습이 없는 모델 선정 기록에서는 학습 성능을 미실시로 명시하고 후보 축소의 판단 근거를 기록한다. 데이터셋 증강 기록은 데이터 **수량 검증**과 이미지 **품질 검증**을 서로 다른 완료 조건으로 본다.
