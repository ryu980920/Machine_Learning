## 최신 교체 이력 — 42번 Grayscale 재제출 (2026-11-09)

- **최신 GitHub 표준:** `02_data/Hand_made/ml26_42.npz`를 새로 받은 `ml26_42(2).zip` 내부 `ml26_42.npz`의 `X`를 기준으로 교체. 현재 42번은 **흑백 반전과 90° 회전 모두 미적용**.
- **원본 SHA-256 (제출 ZIP):** `8f9748b8ae9a053e3d058dcb53dab3a35b0e328dd9387f36dc3d04c1507623be`.
- **새 표준 `ml26_42.npz` SHA-256:** `f364fb453d05b4fe2a705c2b8a80683b404608c7c257d664e3ec7ac86932d4c5`.
- **형식:** 키 `img`, `label`, `label_id`; `img` `(640,28,28)` `uint8`, `label` `(640,)` `<U1`, `label_id` `(640,)` `uint8`; 숫자 0–9 및 문자 A–F 각각 40장.
- **새 42번 밝기 분포:** 고유 밝기값 256종, 16–239 중간 밝기 비율 **11.38%**, 1–254 중간 밝기 비율 **19.59%**. 검은 배경·밝은 글자, 육안으로 정상 방향 확인.
- **원본 픽셀 보존:** 제출 ZIP의 NPZ `X`와 새 표준 `img`가 완전히 동일. ZIP 안의 JPG 640장은 전부 28×28 Grayscale이며 NPZ `X`와 픽셀 차이 최대 2단계(JPEG 재인코딩 차이). JPG를 다시 읽어 쓰지 않고 원본 NPZ의 `X`를 그대로 사용.
- **재현 검증:** 개정 `convert_hand_made.py`를 기존 `ML-Project.zip` 및 새로운 `ml26_42(2).zip`에 적용하면 4개 표준 NPZ 모두 기존 41·43·44와 새 42 각각의 기대 SHA-256을 재현한다.
- **이전 실험과 분리:** 아래의 42번 고유 밝기값 4종·반전·90° 회전 및 성능은 **과거 실험 3에서 사용한 구 42번 데이터의 작업 이력**이다. 구 데이터셋은 Git 커밋 이력에 보존되며, 실험 3 재평가는 아직 수행하지 않았다.

## 1. 과거 실험 3 데이터 제작 순서와 차이점 (v3, 기록 보존)

| 단계 | 적용 대상 | 실제 처리 | 모델 평가와의 관계 |
|---|---|---|---|
| 1. 원본 확인 | JPG 2,560장 | `PIL.Image.convert("L")`로 28×28 중간 밝기 정보 유지 | 변환 전 입력 확인 |
| 2. 흑백 극성 통일 | **42·44번** | 최초 흰 배경/검은 글자 → `255 - gray`로 반전. 41·43번은 반전하지 않음 | **최초 테스트 이전에 적용**; 반전 전후 정확도를 따로 측정하지 않음 |
| 3. Grayscale 초기 평가 | 41·42·43·44번 | 4개 NPZ, 각 640장, 5개 저장 모델로 2,560장 추론 | 방향 미보정 Accuracy 19.88–23.12% |
| 4. 오류 조사 | 4개 작성자 이미지 | 41·42·44번이 43번에 비해 **90° 돌아간 것**을 확인 | 이미지 비교 및 작성자별 오류 검증 |
| 5. 방향 보정 | **41·42·44번** | `np.rot90(images,k=1,axes=(1,2))`로 반시계 방향 90° 회전; 43번 그대로 | 5개 동일 저장 모델로 재평가, Accuracy 53.24–62.93% |
| 6. 최종 파일 확정 | 4개 NPZ | 42·44 극성 반전과 41·42·44 방향 보정 **모두 적용** | 현재 GitHub 표준 입력 |

**중요:** 42번 원본 JPG에는 고유 픽셀 밝기값이 **4종**만 존재한다. Grayscale으로 저장하고 극성을 반전해도 회색 단계는 4종이므로 인공적인 밝기값을 생성하지 않았다. 원본에 존재하는 픽셀값만 보존하며 **임계값 이진화·리사이즈·중심 정렬·추가 증강은 하지 않았다.** 회전은 `np.rot90` 배열 재배치이므로 보간을 수반하지 않는다.

## 3. 과거 42번 기준 밝기 분포 및 재현성 확인 (v3)

| 작성자 | 고유 밝기값 종류 | 중간 밝기(1–254) 픽셀 비율 | 보정 후 평가 Accuracy 범위 (모델 5개) |
|---|---:|---:|---:|
| 41번 | 256종 | 28.54% | 44.53–59.38% |
| **42번** | **4종** | **1.76%** | **49.38–69.38%** |
| 43번 | 256종 | 14.06% | 55.94–66.09% |
| 44번 | 256종 | 14.21% | 58.28–68.44% |

- 당시 `02_data/notebooks/convert_hand_made.py` 구 버전을 원본 `ML-Project.zip`에 대해 **독립 재실행**해 4개 NPZ의 결과를 실험 3에서 사용한 보정본과 비교했다. **네 파일 모두 바이트 단위로 동일**했으며 위 SHA-256과 일치했다.
- 41·42·44번의 회전 변환은 픽셀값의 빈도를 바꾸지 않는다. 43번은 파일 자체가 변경되지 않았다.
- 이 비교는 **작성자마다 다른 획, 필체, 원본의 밝기 분포 효과까지 통제한 실험은 아니다**. 42번이 밝기 단계가 적다고 해서 정확도 저하 원인이라고 확정할 수 없다.
- **보정 전 기록을 덮어쓰지 않음:** 교체 이전 Grayscale NPZ는 이전 Git 커밋에서 복구할 수 있고, 보정 전/후 평가 수치는 EXP-유-004 로그 및 두 CSV에 남겨 두었다.

## 4. 변환 재현

```bash
pip install numpy pillow
python 02_data/notebooks/convert_hand_made.py --source /path/to/ML-Project.zip \
  --writer42-replacement '/path/to/ml26_42(2).zip' \
  --output-dir 02_data/Hand_made
# 새 42번 ZIP이 없으면 덮어쓰기를 방지하기 위해 종료됨
```

**현재 및 후속 실험 입력 규칙:** 현재 `img`는 이미 0–255이므로 **`*255`를 추가 적용하지 않는다**. SVC·MLP·KNN의 저장 Pipeline 내부 `/255` 단계는 그대로 유지한다. 교수님 공식 Test 16,000장은 이 데이터 생성·실험 3에 사용하지 않았다.
